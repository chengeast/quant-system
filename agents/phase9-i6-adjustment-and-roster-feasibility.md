## §2 ① 复权三路径核实（逐条 + 证据 + 交叉验证判定）

### 2.1 路径 A · `gbbq` 是否存在「公开开源、免费、本机、无 key」的 TDX 解密算法

**本机只读结构复验（盘上事实，非照抄秘书申报）**：

| 项 | 实测 |
|---|---|
| 文件大小 | **5,931,171 B** |
| 头 4B uint32 | `eb 1e 03 00` = **204523**（记录数） |
| payload / 整除 | 5,931,167 B = **204523 × 29 B**，`divides_exactly=True` |
| 头 16B hex | `eb1e0300631224b0f311c9a953c0bb18` |
| rec0 前 29B | `631224b0f311c9a953c0bb1806866a39dcbc5c5514c3e1d2000000803f` |
| rec1 前 29B | `631224b0f311c9a9b1e786c097f3e81ca0ae101bb36641e14523909745` |
| 前 8B `631224b0f311c9a9` | 前 10 条抽样记录 **10/10 重复**（ECB / 固定密钥加密特征） |
| 前 9B `631224b0f311c9a953` | 仅 rec0 出现（rec1 第 9B 为 `b1`）→ **「前 9 字节相邻记录重复」的秘书表述应精确化为「前 8 字节重复」**，如实修正 |
| 后 5B 明文（10 条抽样） | `000000803f`、`4523909745`、`4000000000`、`45a83c0c46`、`4100000000`… 为 float 数值，**无可读 6 位代码 / YYYYMMDD 日期** |

**公开资料核实（WebSearch，2026-11-15，资料层面、非本机验证）**：
- CSDN《通da信股本变迁gbbq权息文件解密》（2021-04-28）：「算法为 **3DES**，每条记录的**前 24 字节加密，后 5 字节没有加密**」，并给出 C 解密核心代码框架（`pKeyNow=key` …）。
- 百度文库《通达信gbbq文件解密方法》：「另一块内存中的数据经多次加载对比，发现内容固定，**长度 4176 字节，应该是自带的密码表**…**直接从内存 dump 出来存为文件就行了**」→ 解密所需的 **key / 密码表须从运行中的通达信客户端进程内存 dump**。
- 百度文库《通达信权息文件(gbbq)》：解密后记录格式 `0-7 股票代码 / 8-11 日期 / 12 信息类型 / 13-16 每10股派几元 / 17-20 配股价 / 21-24 每10股送几股 / 25-28 每10股配几股`，「信息类型=1 为除权除息，>1 为股本变动」。
- mootdx / pytdx 为**免费开源**的通达信数据读取封装库（`pip install mootdx`、离线 `Reader` 读 `.day`/`.dat`），但资料未显示其提供「纯本机、无 key」的 `gbbq` 3DES 解密；且 `pytdx` 在线用法要求「**运行着通达信客户端并保持登录状态**」。

**判定：🔴 路径 A 不可行（本批约束下无法「解出并验证通过」）**，理由逐条：
1. **拿不到 key**：3DES 解密依赖 4176B 固定密码表，公开资料明示须从**通达信客户端进程内存 dump**；本批红线「本机只读、不启动客户端、无令牌 / 密钥、无 key」→ 无法取得该密码表；本机 `gbbq` 前 24B 实测非明文、无标准库解密表。
2. **交叉验证缺基准**：派活单要求「若解出，须与 `sh600000` / `sh600519` / `sz000001` 等**已知送转除权事件** + `base.dbf` 股本变动交叉核对，写明验证样本与误差」。本机 `base.dbf` **每证券仅 1 条当前快照**（见 §2.2），无历史除权事件序列；外部「已知送转除权事件」ground truth 需联网取得，本批不联网拉行情 → **无法完成「已知事件交叉验证」，也就无法申报「验证样本与误差」**。
3. **不得脑补 / 硬凑**：红线严禁脑补复权因子；未解密即硬编码「复权因子」属把未复权冒充复权。

### 3.2 判定：不执行「排除当前 ST」

派活单口径：「本机若能**可靠读出当前 ST 名称** → 排除当前 ST 并留痕（写明数据来源、解码方式、命中只数、是否可靠）」。本批实测：
1. `ds_stk.dat` 不含沪深主板 A 股当前 ST（0 命中），只覆盖新三板 / 北交 / B 股；
2. `profile.dat` 是历史曾用名序列，不是当前状态；
3. 两表交集 0、格式未验证、名称时效性不明。

→ **「可靠读出」不成立**。按红线「**严禁编造名录、严禁把『当前 ST』冒充『历史 ST 全过滤』、严禁把『确认存在』写成『已落盘 / 已排除』**」：**本批不落盘任何 ST 排除名单、不在阶段二脚本里执行 ST 排除**，只在阶段二 json / 报告里如实标注 `current_st_exclusion = NOT_APPLIED_UNRELIABLE_SOURCE` 并写明上述证据。**不把「文件里找到 ST 字样」写成「已排除 ST」。**

> 附加口径（必须写进最终报告）：即便将来能可靠读出**当前** ST，用它去过滤 **1998-09-15~2026-11-13 全历史**回测，等于「用当前状态过滤历史」，会引入另一种偏差；**「排除当前 ST」≠「历史 ST 全过滤」**。

### 3.4 ⚠️ 幸存者偏差的准确表述（**原样写进最终报告，不得粉饰**）

> `D:\tdx\vipdoc` 是**当前在市** `.day` 快照，**退市股日线文件根本不在池里** → 「排除退市名录」只能确认**池内当前无退市股**，**无法消除回测期内「后来退市的股票当时应在池里」造成的偏差**；要真正消除偏差需**历史全名录 + 退市股历史日线**。**严禁把「已排除退市 = 已消除偏差」写入报告。**

池内旁证：`_manifest.json` `library_latest=20261113`、`n_stocks_actually_converted=5687`、按代码前缀从当前在市 `.day` 文件筛出（纳入 5687 + 剔除 4493 = 10180 全库文件数），**池内 5687 只均为当前在市快照**；回测期内已退市个股的 `.day` 不在池内，本机无法补入。
